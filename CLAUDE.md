# HashDash v2.2

Forensic file hashing and copy verification tool for Windows, used in digital forensics workflows to produce court-admissible evidence of file transfer integrity.

## Tech Stack
- C# 14, .NET 10, WPF
- Visual Studio 2026
- MVVM pattern (no MVVM framework — manual RelayCommand, BaseViewModel, SetProperty)
- QuestPDF for PDF report generation
- SQLite via System.Data.SQLite for process logs
- Windows CopyFile2 API for forensic file transfers (FileCopyService)
- System.Text.Json for settings and session JSON output

## Key Files
- `ViewModels/MainViewModel.cs` — all application logic (~1,800 lines). Single ViewModel for the entire app.
- `Views/MainWindow.xaml` — main UI
- `SettingsWindow.xaml` / `SettingsWindow.xaml.cs` — settings dialog (Database + Automation tabs)

- `Services/PdfReportService.cs` — QuestPDF A4 report generation (`GenerateManualExportPdf` is the active method)
- `Services/ExportService.cs` — CSV export with chunking
- `Services/DetailedLogService.cs` — in-memory detailed text log, manually exported by user (NOT auto-saved)

- `Services/FileIntegrityService.cs` — captures file metadata at load, detects modification during processing

- `Services/FileNamingService.cs` — generates export file names

- `MtpDevicePickerWindow.xaml` / `.xaml.cs` — device picker dialog for Connect Device

## Operating Modes

### 1. Hash Only
Computes MD5 and/or SHA-256 for each selected file without copying. Status: `Hash Complete`.

### 2. Copy & Verify (Primary)
- Hashes source file
- Copies to primary destination preserving relative directory structure (via CopyFile2)
- Hashes destination file
- Compares — status: `Verified`, `Verified (Existing)`, or `Hash Mismatch`

### 3. Copy & Verify with Secondary (Backup)
Same as above, then copies to a second destination and verifies independently.
- Requires primary destination to be set first
- Status combinations: `Verified (Primary + Secondary)`, `Verified (Primary + Secondary Existing)`, `Verified (Secondary Mismatch)`, `Verified (Secondary Failed)`, `Primary Failed / Secondary OK`, `Failed (Both)`

## Case Metadata (Required Fields)
- **Examiner Name** — free text, required
- **Lab Case Reference** — free text, required
- **Exhibit Reference** — free text, required
- **Computer Name** — auto-populated from `Environment.MachineName`

IDataErrorInfo validation applies to all three required fields. Errors are only shown after the first run attempt (`_hasAttemptedRun` flag).

## File List
- Source folder loaded recursively via `Directory.EnumerateFiles`, batched in groups of 500 for UI performance
- Supports local paths and UNC network paths (`\\server\share`)
- Also supports MTP-connected devices (phones, cameras, drone controllers) via "Connect Device" — see MTP Device Support below
- Displayed via `FilesView` (ICollectionView over `Files` ObservableCollection) — never bind directly to `Files`
- **Status filter**: All / Verified / Failed & Mismatch / Hash Complete / Cancelled / Pending
- **Search**: filename, status, MD5, SHA-256, dest hashes, file date, transfer date, size
- Per-file checkbox selection; Select All tri-state checkbox
- Disk space check against destination before starting copy

## Session ID
Generated once per extraction, immediately after `_processStartTime = DateTime.Now`.

**Format:** `{LabCaseRef}_{SourceDriveLabel}_{DestDriveLabel}_{yyyyMMdd_HHmmss}`

Example: `CASE123_USB001_PROCESS01_20260510_142530`

- Stored in `_sessionId` field on MainViewModel
- Included in: PDF report header, session JSON file
- Drive labels fall back to `"SRC"` / `"DST"` if empty

## Outputs After Successful Extraction

All outputs are generated only when a destination path is set (i.e. Copy & Verify mode).

### PDF Report
- Generated by `PdfReportService.GenerateManualExportPdf()`
- Saved to: `[DestinationPath]\Data Transfer Logs\{ExhibitRef}-{CaseRef}_{dd-MM-yy_HH-mm}.pdf`
- Chunked at **1,000 rows per file** (multi-part suffix `_part01`, `_part02`, etc.)
- Contents: Session ID, case metadata, examiner, computer, start/end time, duration, source/dest paths and labels, per-file hashes and verification status
- Session ID displayed in header in monospace font below Duration row

### Session JSON
- Generated by `GenerateSessionJson()` in MainViewModel
- Saved alongside PDF: `{ExhibitRef}-{CaseRef}_{timestamp}_Session.json`
- Fields:
  - `SessionId` — unique session identifier
  - `AppVersion` — e.g. `"2.2"`
  - `TransferStatus` — `"Pass"` (all verified) / `"Fail"` (none verified) / `"Partial Transfer"`
  - `TotalDuration` — `"HH:MM:SS"` format
  - `PcGuid` — Windows MachineGuid from `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid`
  - `ExaminerName`, `LabCaseRef`, `ExhibitRef`, `ComputerName`
  - `SourcePath`, `SourceDriveLabel`, `DestinationPath`, `DestinationDriveLabel`
  - `SecondaryDestinationPath`, `SecondaryDestinationDriveLabel`
  - `Md5Enabled`, `Sha256Enabled`
  - `StartDateTime`, `EndDateTime` (ISO 8601 roundtrip format)
  - `FileCount`, `TotalSizeBytes`
- No file listing in the JSON — session-level summary only

### Detailed Text Log (Manual Export Only)
- Built in memory during processing by `DetailedLogService`
- **NOT auto-saved** — user must click "Export Detailed Log" button
- Exported as `.txt` via SaveFileDialog
- Contains per-file hash values, copy durations, verification results, and summary

## Database
- **Default path**: `[AppDir]\Logs\ProcessLog.db` (created automatically)
- User can override path in Settings → Database tab
- SQLite with WAL mode for concurrency
- Tables: `ProcessLog` (one row per session), `FileResults` (one row per file per session)
- Schema migration: `AddColumnIfMissing()` adds new columns to existing databases without data loss
- All sessions auto-logged; browsable via the Process Logs window (`LogsWindow`)

## Automation Mode
- `FileMonitorService` wraps `FileSystemWatcher` on the source folder
- **Trigger file**: configurable filename, default `ExtractionSummary.pdf`
- Can include subdirectories (default: on)
- Optional startup delay before processing (default: 2 minutes, configurable 0–60)
- When trigger file is detected: loads source files → optional delay → runs extraction automatically
- Fields locked while automation is enabled
- Requires: Examiner Name, Lab Case Reference, Exhibit Reference, Source Path, Destination Path, at least one hash algorithm
- Banner shows automation state; toast notifications on completion/failure

## MTP Device Support
- "Connect Device" button next to Browse Source Folder, opens `MtpDevicePickerWindow` to list currently-connected portable devices (`MtpDeviceService.GetConnectedDevices()`)
- Uses the `MediaDevices` NuGet package (wraps the Windows Portable Devices COM API) — source only, never a destination
- Connects read-only: `MediaDeviceAccess.GenericRead` / `MediaDeviceShare.Read`; never calls any write/upload/delete/rename method on a device. Logged to chain of custody as "MTP Device Connected — Read-Only Session Requested"
- Full Hash → Copy → Hash → Compare rigor preserved: source is hashed via a real `Stream` from `MediaFileInfo.OpenRead()` (through `HashService`'s `Func<Stream>` overload) before copy, exactly like local/network sources
- Copy uses `FileCopyService.CopyFromStreamWithProgressAsync` (chunked stream copy) instead of `CopyFile2`, since MTP paths aren't Win32 paths
- All WPD COM calls — connect, enumerate, `GetFileInfo`, and every stream `Read()` during hashing/copying — are funneled through one dedicated STA thread inside `MtpDeviceService` (`StaExecutor`). WPD COM objects are apartment-sensitive; without this, calls from arbitrary `Task.Run` thread-pool threads can get silently marshaled onto (and freeze) the WPF UI thread with no visible progress
- `MediaDevice.GetDevices()` returns a static, library-cached instance per device ID (not fresh per call) — never call `.Dispose()` on listed devices just to read identity; `IsConnected` only reflects what the app last did, not whether the driver silently closed the session (iOS does this aggressively on re-lock) — `MtpDeviceService.ExecuteWithRetry` retries once with a forced reconnect on `COMException`
- iOS devices only expose DCIM (Camera Roll) via this path, not general storage — an Apple/AFC platform restriction, not something HashDash can extend
- `FileHashEntry.IsMtpSource` / `MtpDeviceId` / `MtpDevicePath` carry the device identity; `FullPath` holds a synthesized display path (e.g. `[DeviceName]\Internal storage\...`) so every string-only downstream consumer (PathHelper, chain of custody, database, exports) works unchanged
- Device scanning shows live progress (files found so far) and supports Cancel via the same `IsCancelEnabled`/`_cts` mechanism as a normal Run

## CopyStatus / VerificationResult Values
| CopyStatus | Meaning |
|---|---|
| `Hash Complete` | Hash-only mode succeeded |
| `Verified` | Copied and hashes match |
| `Verified (Existing)` | File already at destination, hashes match |
| `Verified (Primary + Secondary)` | Both destinations copied and verified |
| `Verified (Primary + Secondary Existing)` | Both existed and verified |
| `Verified (Secondary Mismatch)` | Primary OK, secondary hash differs |
| `Verified (Secondary Failed)` | Primary OK, secondary copy failed |
| `Primary Failed / Secondary OK` | Primary failed, secondary succeeded |
| `Hash Mismatch` | Copy done but hashes differ |
| `Failed (Both)` | Both destinations failed |
| `Failed` | General failure |
| `Cancelled` | User cancelled |

## Architecture Notes
- `MainViewModel` binds UI to `FilesView` (ICollectionView), never to `Files` directly — always refresh the view after filter changes
- `IDataErrorInfo` on ExaminerName, LabCaseRef, ExhibitRef — errors only surface after `_hasAttemptedRun = true`
- `Dispatcher.Invoke` (blocking) is used for final status writes after all `InvokeAsync` callbacks have drained — do not change to `InvokeAsync` for those writes
- `_fileProgressActive` is a `volatile bool` that guards progress callbacks; set to `false` before the final `Dispatcher.Invoke` to prevent stale UI updates
- `StatusBrush` in `FileHashEntry` is computed from `CopyStatus` at runtime (theme-aware); no static color assignments in XAML
- `PdfReportService.GenerateReport()` is legacy/unused — the active method is `GenerateManualExportPdf()`
- `AppSettings` is stored in the app directory (not AppData) so it stays with the executable
- No MVVM framework — `RelayCommand`, `BaseViewModel`, and `SetProperty` are manual implementations in the Helpers/Commands folders
